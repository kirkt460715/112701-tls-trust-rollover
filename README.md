# 生态监测上传服务的 TLS 信任轮换核验

分钟用任务周期的相对值。证书标识是合成代号，记录只含链、状态和验证结论。 资料均为本地合成记录。

以 Python 3.11.2 运行，无第三方依赖。`records/` 中的 `pki`、`clients`、`gateways` 对应独立来源。每份材料是 JSON 对象数组，`id` 在同一来源内唯一。报告和观察的时间以各原始记录给出的字段为准。

```sh
python3 -m unittest -v
python3 records_view.py
python3 rotation_report.py
```

## 读取资料

资料入口列出来源、记录标识及条数。通过 `--source` 指定来源，`--offset` 和 `--limit` 限定读取的位置与数量。`--records` 可指定同样结构的其他资料目录。

## 办理轮换

`rotation_report.py` 按服务、入口、站点三层核对轮换证据。默认的核对时点是记录中最晚的已知时点，可用 `--as-of` 指定其他时点，用 `--service`、`--entry`、`--client` 收窄，`--json` 输出完整结构。

结论标签：`stable_new`（新链两侧就绪，可稳定使用）、`overlap_active`（重叠期内旧链仍可依赖）、`at_risk`（旧链已停而新链未就绪，站点可能中断）、`blocked`（缺批准或信任，暂不能签认）、`partial`（部分入口可先办，其余仍有缺口）。

核对规则：

- **三类证据分开核对。** 网关接单（`staged`）、实际生效（`applied`，必须晚于批准）和客户端后续观察（`observation`）各自成立才算数。`queued` 的受理状态不算生效。
- **计划不算生效。** 客户端 `next_root` 只是升级计划，`next_root` 计入不了已信任的根；只有 `root` 里列出的根才算已确认。
- **入口之间不能互相签认。** 同一服务的每个入口单独核对；共用一张链时，一处生效或观察不能替另一处作数。
- **撤销优先于维护单。** 旧链的停用时点是自身有效期与撤销生效的较早者；撤销通知到达即关闭回退，即使已有维护单批准过重叠期。
- **重叠期要能核对三件事。** 旧链可用到哪（`old_usable_until`）、新链哪天才两侧就绪（`new_ready_from`）、何时必须停止依赖旧链（`must_stop_relying_at`），都取自原始记录。
- **回执与停用时点冲突单独标注。** 捕获时仍可信、但回执晚于停用时点到达的观察会标成 `conflict`，不能据此继续签认。
- **缺口写明负责方。** 未满足的部分给出 `missing_evidence` 和 `owner`（变更审批人、网关值班台或客户端维护人）。
- **保留审批依据。** `approval_basis` 记载网关接单、客户端确认与撤销记录，便于回查当初的依据。
